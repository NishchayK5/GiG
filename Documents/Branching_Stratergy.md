# Branching Strategy

In iteration 1, we will adopt a simple and more manageable branching strategy. The team is comparatively new to the git environment so we focused on keeping it clear and beginner-friendly. During the team meetings, we discussed the features to target for iteration 1, and listed the tasks required to implement those features. With mutual agreement, we divided the tasks and assigned responsibilities to ourselves. Under main, we created two branches - develop and staging. Each team member created their own branch to work on. 2 members worked on backend and 2 members took the responsibility of designing the UI. We regularly communicated about the changes we were making and pushed the commits to develop branch, and pulled from the develop branch to get regular updates made to the code and ensured our changes are tested before every push. This approach allowed us to work collaboratively while minimizing merge issues and maintaining progress. Then develop branch is pushed to staging branch where our QA tested it working, before deploying the code and pushing it to the main branch for submission.

This strategy worked fine for us, but moving forward for Iteration 2, where we need implementation of higher complexity features, we want to switch the strategy to making branches dedicated to the features. Now, when we are familiarized with the git-workflow, we will introduce a formal-feature branch workflow. Once a feature is completed and tested, then it will be pushed to the staging branch.
